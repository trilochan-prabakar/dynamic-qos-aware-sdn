## 2. Approved engineering decisions

Follow these decisions throughout implementation.

### A. Path optimization objective

Retain the existing NetworkX shortest-path objective.

The controller currently calculates edge costs using reciprocal edge scores and selects paths by minimizing the sum of edge costs.

Make all path comparisons consistent with this objective.

Implement a reliable path-cost calculation that:

- Sums the costs of all edges in a path.
- Uses the same cost values as `_best_path()`.
- Handles single-switch paths correctly.
- Rejects missing, invalid, negative, NaN, or infinite costs.
- Handles paths that are no longer valid in the current topology.

Do not replace the existing optimization algorithm.

### B. Rerouting threshold

Retain the configured 15% threshold.

A reroute should occur only when the new path has strictly more than 15% lower aggregate cost than the old path.

Mathematically:

`new_cost < old_cost * 0.85`

Exactly 15% improvement should NOT trigger rerouting.

Handle zero, invalid, and non-finite costs safely.

### C. Forward and reverse flow tracking

The existing controller tracks forward and reverse flow entries.

Ensure that successful rerouting updates both directions consistently.

For a symmetric undirected topology, the reverse path should be the reversed forward path.

Avoid processing the same flow pair twice during a single monitoring cycle.

Do not assume installation succeeded when required flow rules could not be dispatched.

### D. Installation success

Inspect `install_path()` and its callers.

Make installation report whether all required flow-mod messages could be dispatched to the required datapaths with valid output ports.

Do not update active-flow state after an unsuccessful or incomplete installation.

Important: Sending an OpenFlow message does not itself prove that a switch successfully installed the rule. Do not claim confirmed switch installation unless an appropriate barrier/error-handling mechanism establishes it.

Avoid introducing a complicated new flow-management architecture.

## 3. Required fixes

Implement the following corrections.

**Fix 1 – Path objective consistency**
- Make `_best_path()` and the rerouting comparison use the same aggregate cost objective.
- Remove the inconsistency between summed reciprocal costs and minimum edge score.
- Ensure invalid metrics cannot silently produce misleading paths.

**Fix 2 – Active-flow state**
- Update stored flow paths after successful rerouting.
- Keep forward and reverse entries synchronized.
- Prevent repeated installation of an unchanged route.
- Avoid processing the same flow pair twice per monitoring cycle.

**Fix 3 – Topology changes**
- Validate previously stored paths against the current graph.
- Handle removed edges and disconnected graphs.
- Handle missing source and destination switches.
- Ensure one invalid flow does not terminate processing of other flows.

**Fix 4 – Threshold correctness**
- Implement the strictly-greater-than-15% improvement rule.
- Handle boundary cases and invalid costs.

**Fix 5 – Single-switch paths**
- Handle paths containing only one switch.
- Do not assign arbitrary infinity values that prevent meaningful comparison.
- Preserve valid same-switch flow behavior.

**Fix 6 – Partial installation**
- Detect missing datapaths and unavailable output ports.
- Report incomplete installation.
- Update tracked flow state only when the required messages have been dispatched successfully.
- Do not blindly delete old flow rules during this milestone.

**Fix 7 – Monitoring resilience**
- Isolate errors while processing individual flows.
- Ensure an invalid flow does not unexpectedly terminate the monitoring loop.
- Add useful logging for failed calculations and incomplete installations.
